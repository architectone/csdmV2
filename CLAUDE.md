# CSDM Deep-Linker Sandbox — project guide

A browser-based **learning tool** for ServiceNow's Common Service Data Model (CSDM). It lets a person build a CSDM graph (business capabilities → applications → services → offerings → infrastructure), validate it against real CSDM relationship rules, and — the heart of the tool — **feel *why* the model exists** through impact analysis, failure simulation, cost/revenue-at-risk, and resilience what-ifs. Every feature should make the user experience the payoff, not just read an explanation.

## Architecture
- **server.js** — Express server. Storage is a JSON file (`csdmData.json`); no database. Loads/validates models, keeps timestamped copies in `backups/`. Runs `migrateModel` + `validateGraph` on save/load. Serves `public/` and `shared/`. Routes: `GET|POST /api/csdm` (read/write the working model), `GET /api/csdm/models` + `GET /api/csdm/model` (the Load dialog's list and fetch), `POST /api/csdm/load` (load a named file from `backups/`) and `POST /api/csdm/load-content` (write a model posted as JSON — what `loadModels.js`'s local-file picker uses; **no backup is taken** on this path), `GET /api/health`. It also owns the Interview *capture* endpoints — `POST /api/interview/capture` / `GET /api/interview/captures`, which write and list the top-level **`captures/`** directory: one timestamped JSON per run holding `input` (what the user typed), `built` (what `buildDraft()` made of it) and `expected` (what they say it should have been). Diffing those three is how the draft builder gets tuned; capture churn is not part of feature commits.
- **interviewParse.js** — the Interview Mode LLM front door (`POST /api/interview/parse`, spec §6). Claude Haiku 4.5 extracts *things* from prose into a JSON schema whose class enum is generated from `nodeTypes` per request. Optional by design: no `ANTHROPIC_API_KEY` (or no `@anthropic-ai/sdk`) → `501 {unavailable:true}` → the client falls back to the lexicon. It never emits edges — see the gotcha below. `GET /api/interview/config` reports whether the parser is usable and `POST /api/interview/config` sets the key at runtime (it is test-called first; a key that fails verification is rolled back and never becomes the configured key) — that pair is what the parser section of the **Config ▾** menu reads and writes (`interview.js` ~L1182/L1189), so a key can be supplied without restarting the server. Also owns **token/cost accounting**: every parse logs its own tokens and dollar cost, and `GET /api/interview/usage` returns the running session total (`PRICING` is USD per *million* tokens — **update it whenever `MODEL` changes**, or the endpoint reports a confident wrong number). Set `INTERVIEW_CREDIT_USD` to have it also report credit remaining and calls-remaining-at-this-rate.
- **shared/** (UMD modules, used by both browser and `tests/`):
  - `csdmSchema.js` — **large, minified, single-line** file. The domain model: **52** `nodeTypes` (class → domain/level/color/prefix/metadataFields) and a ~4,885-entry `relationshipRules` array (allowed `{fromType,toType,label,explanation}`). Infra classes form a full "mesh" (every infra type × every infra type × 7 labels); business/service relationships are curated. **Edit this with small Node scripts, not hand edits, then verify by `require()`.** Helpers: `getAllowedRelationship`, `getRulesFromType`, `getValidRelationshipLabels`, `getMetadataFields`, `infrastructureTypes` (a **function**, not an array — call it; returns the 31 infra classes), `visuals.domainMap`. `level` is a depth number (Business Capability 1 … Container Image 10 … Data Center 13, Availability Zone 14, Cloud Region 15) and Interview Mode nests infrastructure by it. Level 16 is the floor and is **not** a class called `Facility` — it is the five `Infrastructure / Facility` classes (UPS, PDU, Generator, CRAC Unit, Chiller).
  - `csdmValidator.js` — `validateGraph(model)`: every node type known, every edge valid.
  - `graphService.js` — edge add/validate/reverse helpers.
  - `migrations.js` — `migrateModel()`: fills domain/position, renames legacy fields, and applies label/type migrations (e.g. legacy `Realizes`→`Provides`, `Business Service Offering`→`Service Offering`). Run on every load/save.
  - `modelState.js` — undo/redo/save/discard container (used by tests; the browser reimplements the same pattern inline).
- **public/**:
  - `app.js` — the whole client engine (also **minified, ~one statement per function**). vis-network rendering with an inline-SVG fallback. Owns `currentModelData`, undo/redo (`markChange`), all dialogs, impact/cascade/lineage/dashboard logic.
  - `index.html` — header (title, `#current-model-name` — the loaded model's name, kept in sync with undo/redo — and About), canvas + zoom controls, the **`#empty-state` Start Here panel** (three cards: Describe your environment → Interview Mode, Open a finished model → the reference example, Build it layer by layer → Guided Path, plus a link into the tour; shown by `syncEmptyState()` when the model is empty and the panel has not been dismissed since, and on demand from **Build ▾ → Start Here**), three right-click context menus (canvas/node/edge), the status bar (left to right: status text, **File ▾** [New/Open/Save], **Config ▾** [two accordion rows — Learning Mode, and the interview parser section which `interview.js` injects into `#parser-config-slot`], **Phase** chips, **Learn ▾**, **Build ▾**, **Analyze ▾**, Undo, Redo, **View ▾**, **Search ▾**), a generic modal, the Inspector panel, and an embedded `CSDM_FALLBACK_DATA`.
  - `loadModels.js` — Load/Save-As dialog; reads `backups/` via `/api/csdm/models`.
  - `interviewLexicon.js` — Interview Mode vocabulary (`window.CSDM_LEXICON`): ambiguity `traps` (service/app/cluster/server/database/environment/instance — always *ask*, never guess), class-match `groups` by area, plus `match`/`split`/`strip`. Every entry carries a `why` teaching line; quantifiers ("two VMs") become a redundancy value, not two nodes.
  - `interview.js` — Interview Mode engine (`window.CSDM_IV` / `CSDM_START_INTERVIEW`). Eight stages, sequenced by `const ORDER` = `anchor → environments → ownership → capability → consumers → infrastructure → resilience → money` ([interview.js:645](public/interview.js:645)) — top-down, the way CSDM itself reads: name the service, then who owns it, what capability it serves, who consumes it, and only then what it runs on. Review is not a stage; it is the screen after the last one. The `STAGE_DEFS` array is deliberately in a different order, so **re-sequence by editing `ORDER` only** — both the stage leads and the questions branch on what is already known, so moving a stage changes wording elsewhere. Every stage is skippable: `skip()` shows that stage's `cost()` (what stops working) before accepting, and `gaps()` recomputes what is missing from the *answers* so an empty Next reads the same as a Skip. Then a `buildDraft()` that proposes nodes/edges as rejectable *claims*, and a commit that runs the cascade and shows the payoff. The infrastructure stage calls `/api/interview/parse` and falls back to the lexicon on any failure (`runParse`/`fromLLM`/`pickTrap`). Injects its launcher into the **Build ▾** menu and the canvas context menu on load.
  - `styles.css` — all styling.
- **scripts/** — one-off schema maintenance, run by hand, not part of the server: `add-phases-and-build-classes.js` (assigns every class its `phase`) and `add-workbook-fields.js` (metadata-field and rule edits derived from the CSDM Data Modeling Workbook). This is the "small Node scripts, not hand edits" route for `csdmSchema.js`.
- **INTERVIEW_MODE_SPEC.md** — the design spec for Interview Mode (question tree, lexicon tables, coverage matrix, open issues). Read it before changing stage wording or the lexicon.
- **tests/run-tests.js** — `node tests/run-tests.js` (5 tests: validator, edge dup, reverse, save/undo/redo, migration).

## CSDM domains modeled (all four — plus two strays)
All four CSDM domains, 52 classes. Note the `domain` field takes **six** distinct values, not four: the four below, plus a bare `Infrastructure` holding the single generic `Infrastructure CI`, and `Build & Integration` holding the single `SDLC Component`. Code that switches on domain has to handle both or those two classes fall through.

Design & Planning, 3 (Business Capability, Business Application, Information Object) · Service Delivery, 10 (Application Service, Technical Service, Technical Service Offering, Application, **Dynamic CI Group**, plus the CSDM 5 **Service Instance** generalization: Data / Network / Connection / Operational Process / Facility Service Instance) · Service Consumption a.k.a. Sell/Consume, 7 (Business Service, Service Offering, Service Commitment, Service Portfolio, Service Catalog, Catalog Item, Subscription) · Infrastructure, 31 across sub-domains `Infrastructure / Compute 4 · Runtime 6 · Data 1 · Storage 1 · Network 5 · Security 3 · Cloud 2 · Physical 3 · Facility 5` plus the bare `Infrastructure` 1 (Facility = UPS, PDU, Generator, CRAC Unit, Chiller — the power/cooling layer under a Rack). `infrastructureTypes()` returns exactly those 31.

## Blank start
**The app ships with an empty `csdmData.json` (`nodes: []`), so a fresh clone opens on the Start Here panel rather than inside a 44-node model nobody built.** Returning users are unaffected: `csdmData.json` is both the working model and the save target, so whatever they last saved is what they reopen. Two couplings had to be handled and must stay handled:
- **The tour no longer opens itself over an empty canvas.** `maybeAutoTour()` checks `currentModelData.nodes.length` *inside* its 900 ms timeout (`loadSandbox()` is async, so the model is not in hand at call time) and Start Here's own tour link is the way in instead — two overlays greeting a first-time user is not a welcome. It deliberately does **not** set `csdm.tourSeen` when it skips, so the tour still auto-runs the first time there is a model to narrate.
- **Three steps carry `needsModel:true`** ("The model reads top to bottom", "Node actions live on right-click", "Impact Analysis") and `tourSteps()` filters them out while the canvas is empty — 8 steps instead of 11 — so the header count and the Done button stay honest. The closing step stays in both cases: on an empty canvas its "Load it now" button is the fastest exit from empty.
- **`initialFullDemo` is gone.** Both Seed Model resets were built from that boot snapshot, which made "Full Demo" mean "whatever you happened to open" and had Minimal Starter reaching into it by *position* (`nodes[0]`, `nodes[4]`) — lucky ordering, and an outright throw on an empty model. Full Demo now reads `EXAMPLE_MODELS.reference` over `GET /api/csdm/model?file=`, Minimal Starter builds its two nodes from the schema and needs no file, and both stay in-memory so Save and Undo still behave.

## Example models (loadable from the Load dialog / `backups/`)
**Every in-app "load an example" button goes through `loadExample(key)` and the `EXAMPLE_MODELS` table in `app.js` — never a hardcoded filename.** That is what let Start Here's "Open a finished model" card quietly load the *reference* example while the tour's closing step told you to go and find the *shared-infra* one; the loader took no argument. Callers: Start Here → `sharedInfra`, the tour's "Load it now" button (`tourLoadDemo()`) → `sharedInfra`, the Business Layer Reference dialog → `reference`. `vmHa` is in the table with no caller yet. Loading writes the file straight over `csdmData.json` via `POST /api/csdm/load`, which takes **no backup** — so do not trigger one while verifying in the browser unless you mean to lose the working model; stub `fetch` and assert the requested filename instead.
- `csdmData.reference-example.json` — single-service reference. It carries **three** edges that look redundant next to the `Contains` hierarchy and are not: `svc-equity-trading --Depends on--> db-orders`, `db-orders --Runs on--> node-pgh-01`, and `svc-equity-trading --Depends on--> workload-order-router`. They are the documented two-edge pattern for a data leaf. Without the first, the Application Service reached the runtime only through the cluster and `Contains` points *downward*, so failing the storage volume reported four infrastructure CIs and **zero** business anchors — the model could not say the volume mattered to anyone. Without the second, the database survives losing its own host. Do not remove any of them as duplicates. **Pod, Container and Container Image are deliberately left off the *business* spine** (0 business anchors when failed) — they are rank-1 replaceable units in `FAILURE_DOMAIN_RANK`, so you swap one and do not page anyone. They still carry their outage to each other: `pod-order-router-1 --Depends on--> container-order-router` exists alongside the `Contains` edge so the container is not a *sink*. Contains carries the pod outage down, Depends on carries the container outage up, the same two-edge shape the data leaves use. That makes pod and container a deliberate **mutual pair** in the impact graph — each reports the other as affected, which is honest for Kubernetes, where they share a lifecycle. `reachFrom()` skips the start node, so the cycle terminates; do not "fix" it by deleting one side. That is a modelling decision about what story the reference example tells, not an oversight; the Workload above them is the level at which an outage becomes the business's problem.
- `csdmData.shared-infra-example.json` — two services sharing infra (impact-contrast demo).
- `csdmData.vm-ha-example.json` — VM/HA cluster + full Service Delivery + Sell/Consume layers, plus the facility layer (rack → PDU/UPS/CRAC) — the richest.
- `csdmData.json` — the current working model. **Ships empty** (see Blank start); `backups/Custom-Edited-Model.json` is the 44-node model it used to hold.
- Also in `backups/`, not examples: `Baseline.json` and `Custom-Edited-Model.json` (plus the timestamped save churn). See Workflow.

### The "why does this exist" surfaces

Four things answer a version of "why is this here", and they answer
*different* questions — do not merge them:

- **Why This Node Matters** (`whyNodeHtml`) — what the node does in the model
  it is actually in.
- **Relationship Details** (`relationshipExplanation`) — why this edge is
  *legal*, straight from the rule's `explanation`.
- **Why This Label?** (`whyLabelHtml`) — why this label rather than the other
  legal ones. Between two infra classes up to **seven** labels validate and
  only `IMPACT_REVERSE_LABELS` carry failure upward, so the dialog re-runs the
  cascade under each candidate label via `withEdgeLabel()` and prints what each
  would report. A legal-but-forward label is the trap that produces a silent
  no-op cascade, and this is the only screen that names it at the moment of
  choice.
- **What Would We Lose Without It?** (`computeOmission` / `omissionHtml`) — the
  counterfactual. Simulate Failure asks what breaks if a node *dies*; this asks
  what the *model* stops being able to answer if nobody modeled it. Those are
  different questions and the second one is the whole reason the non-operational
  classes (Business Application, Business Capability) are worth modeling at all
  — they cannot be failure-simulated, so the omission analysis is the only place
  their value is measurable.

`computeOmission` diffs four things across the removal: new `analyzeModelQuality()`
findings, loss of reachability to a `BUSINESS_ANCHOR_TYPES` node, per-node
cascade shrink, and revenue that becomes unattributable.

- **The coach delta is deliberate reuse.** New findings are matched by `.text`
  against the before-set and rendered with the Coach's own `why` prose, so the
  two screens cannot drift. Their `edge:` indices are **stale** after removal —
  never render a Highlight button from an omission finding.
- **It is deliberately not phase-gated**, unlike Coach findings. "That is a
  Run-phase concern" is the wrong answer to "why does this need to exist".
- **`withoutElement()` and `withEdgeLabel()` temporarily reassign the
  module-global `currentModelData` and restore it in a `finally`.** Only call
  pure compute inside them. Anything that renders, calls `markChange()`, or
  persists will operate on the hypothetical model and either corrupt undo
  history or save a model the user never built.
- `OMISSION_MAX_NODES` (400) caps the per-node cascade comparison, which is
  O(n²); above it that section is skipped and the dialog says so.

## Conventions & gotchas (READ BEFORE EDITING)
- **Schema changes (`shared/csdmSchema.js`) require a SERVER RESTART** — `server.js` `require()`s the schema once at startup, so the browser sees new classes on refresh but server-side validation still uses the old copy until restart (a load will fail "validation failed" until then). `public/*` changes only need a browser refresh.
- **`public/app.js` and `shared/csdmSchema.js` are minified one-liners.** After ANY edit run `node --check public/app.js`. In single-quoted JS strings, apostrophes break the file (a past bug) — prefer template literals / backticks for any prose.
- **EA vs ServiceNow naming is intentional dual-naming.** UI labels use clear EA terms; the real ServiceNow relationship/class names are shown on hover, in the Inspector, and in Reference/Classes tables via `SERVICENOW_REL` / `SERVICENOW_CLASS` maps in `app.js`.
- **Impact direction:** `IMPACT_REVERSE_LABELS` in `app.js` decides which edges propagate failure target→source (Depends on/Runs on/Uses/Instantiates/Offers) vs source→target (Contains/Routes to/Points to/Provides/Realizes).
- **Non-operational types** (`NON_OPERATIONAL_TYPES`) can't be failure-simulated (Design + Sell/Consume artifacts).
- **Resilience is scope-ranked, not boolean.** `FAILURE_DOMAIN_RANK` (one replaceable unit — Physical Host/VM/Compute Node/Pod/Container/UPS/PDU/Generator/CRAC Unit/Chiller — 1, Rack 2, Data Center 3, AZ 4, Cloud Region 5) vs `REDUNDANCY_SCOPE_RANK` (`Redundant pair` 2, `HA cluster`/`Auto-scaling` 4) in `app.js`: a node absorbs a failure only when its redundancy rank ≥ the origin's domain rank. Nothing reaches 5 — losing a region is deliberately unsurvivable, and Interview Mode ends on exactly that.
- **Absorption requires a failure *domain* as the origin — `originRank > 0` in `computeCascade`.** Redundancy protects you from losing *some of yourself*, never from losing something you depend on. A rack or zone kills the replicas inside it and leaves the rest, which is what a wider scope survives; a discrete component dying (Database Instance, Storage Volume, Facility Service Instance, Application Service) is a *total* loss with no scope, and every replica of every dependent sits behind it. Without this guard the unranked default of 0 made every resilient node absorb every dependency failure — in `csdmData.json`, losing `cr-orders-vol` affected **zero** nodes because the redundant database "absorbed" its own storage disappearing. **The rank-1 list is load-bearing for that guard**: those are units you swap one of, so their loss is partial from above. Get it wrong in either direction and the cascade lies — omit `VM` and an HA cluster stops absorbing a single node; add `Storage Volume` and a database survives losing the disk it lives on.
- **A service can end up a dependency of itself, and `dropSelfTerms()` is the only thing stopping it.** A sentence like "the billing portal runs on two app servers" names the service inside its own infrastructure answer. Whatever was given as the anchor or the application gets pulled back out of the term list and *said out loud on the next screen* — a silent drop would be a silent guess. Infrastructure is now asked *after* the service is named (see `ORDER` above), so the parse already knows the anchor: the primary hook is inside `normalizeInfra()` ([interview.js:171](public/interview.js:171)), placed there deliberately so no future parse path can skip it. The anchor and ownership reads call it too, as backstops for a rename *after* the infrastructure stage. It is idempotent, so extra calls are free. `buildDraft()` must also tolerate a null `prodId`/`appId` and empty `capIds`, because any stage can be skipped.
- **Interview Mode must only emit `IMPACT_REVERSE_LABELS` edges** for the dependency spine (`pickLabel` in `interview.js`). Using `Contains` there would look correct on the canvas and silently produce no cascade — the whole point of the feature dies. Same reason data/network/security leaves hang off the *Application Service*, not off whatever VM happened to be placed last.
- **`level` is depth from the business, NOT hosting order.** `Database Instance` is 8 and `VM` is 6, yet the database runs *on* the VM. Never derive hosting parentage from `level` for data/storage/network/security classes — doing so was why a database never landed on its host. `buildDraft()` stacks only `HOSTING`/`RUNTIME` classes by level; everything else gets **two** edges: `Application Service --Depends on--> X` (carries X's outage up to the business) *and* `X --Runs on--> <box>` (carries the box's outage down to X). Emitting only one leaves a database that survives losing its own VM. `csdmData.json` has both — check any topology change against it.
- **The LLM extracts things and *pairings*, never relationship labels.** `interviewParse.js` returns nodes plus optional `runsOn` / `dependsOn` holding the *user's own sourcePhrases* — which things are joined, never how. `pickLabel()` in `buildDraft()` still chooses every label, so only `IMPACT_REVERSE_LABELS` can reach the graph. Do not let the model emit a relationship type. Do not "improve" it by letting the model emit edges. It is likewise not allowed to resolve an ambiguous term — `ambiguous:true` routes back into the hand-written traps, because the question *is* the teaching. Prompt caching there is real but only engages above **4096 tokens** on Haiku 4.5; the endpoint logs the cache hit per call, so check that before assuming it works. **Measured: it does not currently engage** — the class-table system prompt is ~1.4k tokens, well under the minimum, so `cache_control` is accepted and silently does nothing. `logUsage()` prints a one-time NOTE saying so on the second call. Growing the schema past ~4k tokens of class table would switch it on by itself.
- **Sandbox classes:** `isPickableClass()` hides classes with no `SERVICENOW_CLASS` mapping from pickers unless the `csdmAllowSandbox` localStorage toggle is on (set from the Classes dialog).
- **Phase scope narrows the three *builders*, never the canvas.** Every class carries a `phase` (Crawl 13 / Walk 30 / Run 6 / Fly 3 = 52 — assigned by `scripts/add-phases-and-build-classes.js`). **Those counts are spelled out in prose in a second place**: the tour's Phase-chips step in `TOUR_STEPS` (`app.js`, 11 steps) says "13 … 30 … the last 9 — 52 classes in all". Reassign a phase and the tour starts lying, so edit both. `activePhases` in `app.js` (the **Phase** chips on the status bar itself, persisted to `csdmPhaseScope` — always visible on purpose, because a mode that changes what the builders create must not hide in a menu; note the modal backdrop at `z-index:30` covers the bar at `z-index:15`, so the chips cannot be toggled while a dialog is open) gates what Interview Mode, Guided CSDM Path and the Topology Builder may *create* — `isBuildableClass()` = `isPickableClass()` **and** `inPhaseScope()`, and a class picker in those three should use it, not `isPickableClass` alone. It deliberately does **not** filter `getFilteredGraph()`: hiding nodes already on the canvas would make impact analysis and the cascade under-report the blast radius, which is the one thing this tool must never do. The scope can never be empty (the last ticked phase is locked) or every builder would have nothing to offer and no control left to switch back on. A class removed from a picker is always explained via `outOfPhaseNote()` — the phase boundary is the teaching, so it is never a silent disappearance. Guided Path steps and Interview stages are *hidden* when their class is out of scope, so `commitGuidedDialog()` and `buildDraft()` must both tolerate every layer being absent and guard each edge on both endpoints existing. Class pickers show the phase as a **text** tag (`Kubernetes Cluster · Walk`) via `classOptionHtml()` / `nodeOptionLabel()` — an `<option>` cannot hold `phaseBadge()` markup. `classOptionHtml()` always writes an explicit `value=""` because the Guided Path type and Topology target-type pickers used to let the option *text be the value*; append anything to that text without a `value` and every commit handler starts looking up a class called `VM · Crawl`. The three remaining value-less options are relationship labels, which have no phase. **Two controls wear the same four words:** the Classes dialog's "Maturity phase" bar is `classPhaseFilter`, a single-select view filter on that table only and not even persisted; the build scope is `activePhases`. The Classes table states the build scope and greys the out-of-scope rows so the two cannot be confused. Dialogs opened *directly* rather than through `openDialog()` must register in `PHASE_AWARE_DIALOGS` (currently `classes` and `stats`) or they display a scope they do not refresh — the Learn panel stays open on top of the modal with the chips live, so this is reachable, not theoretical.
- **View Mode and Relationship filters are multi-select** (`activeViewModes` / `activeRelationshipFilters`, both arrays). Views **union** their node sets; relationship labels are **OR**ed. `full` and `all` are absorbing — picked with anything else they collapse to themselves. Never assign `.value` on those two `<select multiple>` elements (it selects exactly one option) — call `syncViewMenuSelects()`, or `setViewModeOnly(m)` when setting state without a re-render.
- **The status-bar menus are split by verb: Learn teaches, Build makes things, Analyze asks the model questions — in that order on the bar.** Build ▾ holds Start Here, then Interview (injected by `interview.js` into `#build-menu-panel .bar-menu-actions`, anchored *after* `#start-here-launch` so the order is index.html's and not whichever script ran last), then the Guided Path, Topology and Relationship builders; Analyze ▾ holds Explain, Coach, Dashboard, 2am Incident Replay and Stats; Learn ▾ holds the tour, Reference, Modeling Traps and Classes. **Start Here is filed under Build, not Learn** — it is titled "three ways into a first model" and two of its three cards launch builders, so it is a front door, not something to read. Before this they were one eleven-entry Learn menu, and — the real bug — Interview sat in it while its three sibling builders were reachable *only* from the canvas right-click, so the one verb the tool exists for had no home on the bar. **The canvas and node right-click menus keep every duplicate deliberately**: they are the faster path once you know what you want, not a legacy leftover to clean up. Sort a new dialog by what it reads: your model (Analyze) versus the same on an empty canvas (Learn). Stats reads your model, which is why it is in Analyze despite feeling like a reference table.
- **Focus is a node right-click item, not a bar button, and the toggle is per-node.** `#focus-selected-btn` is gone; `#node-menu-focus` calls `toggleFocusNode(id)`, whose one subtlety is that it only *unfocuses* when the node under the cursor is the one already focused (`isFocusedNode`) — focused on A and right-clicking B has to move the focus to B, and a plain `toggleFocus()` would have cleared it instead. The node menu relabels itself to `Unfocus (back to the full model)` with the amber `.focus-active` class when you right-click the focused node, which is the only "you are in a filtered view" cue left on that path besides `View: Filtered`. It used to sit first in the node menu; it now sits third, below **Why This Node Matters** and **What Would We Lose Without It?**. Focus is still the shortest-travel item for someone who knows what they want, but the two "why" items are the ones a novice needs to stumble into, and stumbling only happens at the top. The old `Show Selected Node Neighborhood` item and its `showNeighborhood()` helper are **gone**: Focus is the same neighborhood view plus centring and the hop count, so keeping both put near-twins three rows apart. The canvas menu's `Selected Node Neighborhood View` is a different entry point (`setViewMode('neighborhood')`, no centring) and stays.
- **Status bar order is File, Config, Phase, Learn, Build, Analyze, Undo, Redo, View, Search — fixed by markup position, not by JS anchoring off a sibling.** Left to right it reads as the order you meet them: learn what this is, build one, then ask it questions. `interview.js`'s `buildParserMenu()` used to insert itself `afterend` of the Learn button, which put it in the wrong slot once Learn moved; it now replaces the `#parser-config-slot` placeholder *inside* `#config-menu-panel` (falling back to appending to that panel if the placeholder is missing, so the worst case is a misplaced section rather than no way to enter a key). Re-sequencing the bar is an `index.html` edit — not a change to `buildParserMenu()`.
- **Config ▾ holds the two settings that change how the builders *behave*; Phase stays on the bar because it changes what they may *create*.** Learning Mode and the interview parser both live in `#config-menu-panel`; neither has a bar button of its own any more. The parser's old always-visible indicator survives as a badge: `paintConfigButton()` in `app.js` is the single writer of that button and composes `Config: LLM · Learn On ▾` (teal when either is non-default, bare `Config ▾` when both sit at their defaults, the same grammar as `View: Filtered`). It owns Learning Mode directly and asks `window.CSDM_IV.parserSummary()` / `parserTitle()` for the parser half, so `interview.js` never writes that button itself — it calls `paintConfigButton()` from `paintParserButton()` whenever a key changes. Two writers there would fight. Opening the menu re-reads `/api/interview/config`: `onConfigMenuToggle` is registered with `addEventListener` on `#config-menu-btn`, which fires *after* the inline `toggleBarMenu` onclick, so the panel's `hidden` class already says whether this was an open or a close. The panel is **two collapsed `.cfg-row` accordion rows** that each state their own value while shut (`Learning Mode … Off`, `Interview parser … Built-in`) — 91px closed against the 397px of the first version, where a one-line select sat above a 340px key form and the two settings did not read as a pair. `toggleConfigRow()` closes the other row on open; `paintConfigRows()` is called from `paintConfigButton()` so the row values, the Off/On pills and the bar badge cannot disagree. The parser section injects *without* a heading of its own because the row already carries one.
- **`#config-menu-panel` carries `.bar-menu-stay`, and removing it breaks the panel in a way that looks like nothing.** Every `.bar-menu` gets a delegated click handler that calls `closeBarMenus()` when any `<button>` inside it is clicked — correct for File/Learn/View, where a button means "do this and go away". Config is all *controls*: clicking a row header would open the row and instantly close the panel around it, and Save & test would close the panel that its own result message renders into. The handler now skips buttons inside `.bar-menu-stay`. This did not bite the old Parser menu only because `interview.js` injected that panel *after* the init-time `querySelectorAll('.bar-menu')` had already run, so it never got the handler — moving the parser into static markup is what exposed it. **Test bar-menu buttons with a real `.click()`, not by calling the handler directly**: calling `toggleConfigRow()` straight bypasses delegation and reports a pass on a panel that would slam shut in a browser.
- **There is no Discard button and no `discardChanges()`.** Removed outright, not hidden — `git log`/`git blame` for history if you need it back. Do not confuse this with `shared/modelState.js`'s own `discard()`: that is a separate, still-live implementation of the same undo/redo/save/discard pattern, exercised by `testSaveDiscardUndoRedo` in `tests/run-tests.js`, and untouched by this change.
- **Node search is a button + scrollable panel, not a text input with a native `<datalist>`.** `#node-search-btn` opens `#node-search-panel` (a `.bar-menu`): the search box sits fixed at the top, `#node-search-list` scrolls below it and is rebuilt on every keystroke by `renderNodeSearchList()`, capped at `NODE_SEARCH_MAX_ROWS` (200). Clicking a row calls `focusNodeById(id)`. `focusNode(n)` is the one shared "select this node and center the canvas on it" implementation — `focusNodeById(id)`, the row click, and the Inspector's Focus buttons all funnel through it, so there is exactly one place that knows how to focus a node. The old `#node-search-options` datalist, its populate step in `populateLargeModelControls()`, and the `searchAndFocusNode`/`findNodeBySearchValue` pair that served it are all gone; do not resurrect a datalist alongside this panel — pick one.
- **New/Open/Save live inside `#file-menu-panel`** (`ids status-load-model` / `status-save-model` unchanged — only the Load button's *label* became "Open"; `window.CSDM_OPEN_LOAD_MODELS` / `CSDM_SAVE_MODEL_AS` unchanged). `loadModels.js`'s `ensureStatusButtons()` only creates a fallback button if the id is missing entirely — the normal path just rewires `onclick`, so it does not fight with the File menu's static markup.
- **Verify in-browser cheaply:** prefer `javascript_tool`/DOM/`getSelectedNodes` checks over screenshots (screenshots are token-heavy). vis-network uses Hammer.js, so synthetic click events don't drive selection — use real clicks or programmatic `selectNodes`.
